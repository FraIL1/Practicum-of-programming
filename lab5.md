## 1. Теория: Проблема оперативной памяти

Представьте, что ваша система из Лабораторной №3 успешно работает в production. Но однажды один из филиалов прислал выгрузку транзакций за 10 лет. Размер CSV-файла — 15 Гигабайт. 

Если ваш код выглядит так:
```python
with open("data.csv") as f:
    data = f.readlines() # Загружает ВСЕ 15 ГБ в оперативную память!
```
Ваш сервер мгновенно упадет с ошибкой `MemoryError` (или ОС "убьет" процесс из-за нехватки RAM — OOM Killer).

Чтобы обрабатывать данные любого объема, мы используем **ленивые вычисления (Lazy Evaluation)**. Мы читаем данные по одной строке (или небольшими чанками), обрабатываем, сохраняем промежуточный результат и забываем прочитанное.

### Итераторы и Генераторы
* **Итератор** — это объект, который реализует методы `__iter__()` и `__next__()`. Он помнит свое состояние и выдает следующий элемент только когда его попросят.
* **Генератор** — это функция, которая использует ключевое слово `yield` вместо `return`. При вызове `yield` функция "ставится на паузу", отдавая значение, а при следующем обращении продолжает работу с того же места.

[Генераторы — это конвейерная лента на заводе. Детали едут по одной, а не вываливаются всей кучей в цех.]

## 2. Техническое задание: "Пайплайн безлимитных данных"

Ваша задача — провести **рефакторинг** (переписывание) вашего `Data Integration Engine` из ЛР №3 так, чтобы он мог обрабатывать файлы любого размера, потребляя при этом не более 50 Мегабайт оперативной памяти.

### Требования к реализации:

#### 1. Генератор чтения
Перепишите слой чтения файлов. Создайте функцию-генератор `read_transactions(file_path: str)`, которая открывает файл и возвращает строки по одной через `yield`.

#### 2. Конвейер обработки (Pipeline)
Обработка данных должна строиться как цепочка генераторов (один передает данные в другой):
1.  Генератор чтения (выдает сырые строки).
2.  Генератор парсинга (превращает строку в словарь или DTO-объект).
3.  Генератор фильтрации (пропускает только валидные транзакции, "битые" логирует и отбрасывает).
*Все эти шаги не должны сохранять данные в промежуточные списки `list`!*

#### 3. Агрегация с O(1) по памяти
Финальный подсчет суммы по категориям должен происходить "на лету". Вы читаете элемент из конвейера, обновляете счетчики в небольшом словаре (он займет мало места, так как уникальных категорий немного) и идете дальше.

#### 4. Доказательство эффективности (Профилирование)
Вам нужно доказать, что ваш код действительно работает "лениво".
1.  Напишите отдельный скрипт `generate_big_data.py`, который создает CSV-файл размером ~1 Гигабайт (заполняет его случайными транзакциями).
2.  В вашем основном коде используйте стандартную библиотеку `tracemalloc`, чтобы замерить пиковое потребление памяти во время обработки этого файла. Оно не должно зависеть от размера файла!

Самое главное правило рефакторинга: **внешнее поведение системы не должно измениться.**
У вас уже есть тесты из Лабораторной работы №4. После того как вы перепишете код на генераторы, запустите `pytest`. **Все тесты должны светиться зеленым.** Если тесты упали — вы сломали бизнес-логику при переписывании.
