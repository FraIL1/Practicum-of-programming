# Лабораторная работа №4: Автоматизированное тестирование и контроль качества


## 1. Теория: Почему «оно работает у меня» — это не аргумент

В профессиональной разработке код без тестов считается «мертворожденным». Тесты нужны не для того, чтобы найти баги сейчас, а для того, чтобы **не сломать всё завтра**, когда вы решите добавить новую функцию.

### Пирамида тестирования
1.  **Unit-тесты (Модульные):** Проверяют одну маленькую функцию в изоляции. Их должно быть очень много.
2.  **Integration-тесты (Интеграционные):** Проверяют, как два модуля работают вместе (например, чтение из файла + валидация).
3.  **E2E-тесты (Сквозные):** Проверяют всю программу целиком от входа до выхода.



### Паттерн AAA (Arrange, Act, Assert)
Каждый хороший тест состоит из трех фаз:
1.  **Arrange (Подготовка):** Создаем нужные объекты, подготавливаем данные.
2.  **Act (Действие):** Вызываем целевую функцию.
3.  **Assert (Проверка):** Сравниваем результат с ожидаемым.

### Фикстуры и Моки (Fixtures & Mocks)
* **Fixtures (Фикстуры):** Позволяют не дублировать код подготовки данных. Например, если 10 тестам нужен один и тот же "чистый" объект базы данных, мы выносим его в фикстуру.
* **Mocking (Имитация):** Это «подмена» реальных объектов. Если ваша функция удаляет файлы на диске, вы не хотите, чтобы тесты реально что-то удаляли. Вы подменяете модуль `os` или `pathlib` на «пустышку», которая просто запоминает, что её вызывали.

## 2. Техническое задание: «Стресс-тест для Интегратора»

Вам необходимо покрыть тестами вашу систему обработки данных из **Лабораторной работы №3**.

### Требования к реализации:

#### 1. Структура тестов
В корне проекта должна появиться папка `tests/`. Тесты должны быть разделены логически:
```text
tests/
├── unit/               # Тесты для Validator и моделей данных
├── integration/        # Тесты для Reader и агрегации
└── conftest.py         # Общие фикстуры для pytest
```

#### 2. Обязательные сценарии (Test Cases)

* **Unit: Валидация.** Проверьте ваш `Validator` на граничных значениях:
    * Сумма = 0.01 (валидно).
    * Сумма = 0 (невалидно, должен быть `ValidationError`).
    * Сумма — очень большое число (проверка на переполнение, если актуально).
    * Некорректная дата или ID.
    * *Используйте `@pytest.mark.parametrize` для проверки 10+ разных случаев в одном тесте.*

* **Unit: Исключения.** Напишите тест, который проверяет, что при подаче «мусора» ваша система действительно выбрасывает `InvalidTransactionError`, а не падает с `IndexError`.

* **Integration: Работа с Файловой системой.** * Используйте встроенную фикстуру `tmp_path`. Она создает временную папку для теста, которая удалится сама.
    * Тест должен: создать временный CSV, записать туда 1 хорошую и 2 плохие строки, прогнать через ваш `Processor` и проверить, что в итоговом JSON только 1 запись.

* **Advanced: Mocking.** * Используйте `unittest.mock.patch`, чтобы сымитировать ситуацию, когда диск «защищен от записи». Проверьте, как ваша программа обрабатывает невозможность сохранить `result.json`. Она должна корректно залогировать ошибку, а не просто вылететь.

#### 3. Покрытие (Coverage)
Вы должны использовать плагин `pytest-cov`. 
* **Цель:** Покрытие кода (Coverage) должно быть **не менее 80%**. 
* Вы должны сгенерировать HTML-отчет о покрытии и убедиться, что все ветки `if/else` в вашей бизнес-логике проверены.

## 📚 Теория: Продвинутые приемы

### Фикстура `tmp_path`
Вместо того чтобы создавать файлы `test.csv` в папке с кодом, делайте так:
```python
def test_csv_reader(tmp_path):
    d = tmp_path / "sub"
    d.mkdir()
    p = d / "hello.txt"
    p.write_text("content")
    assert p.read_text() == "content"
```

Не пишите 5 тестов для разных сумм. Пишите один:
```python
@pytest.mark.parametrize("amount, expected_valid", [
    (100.0, True),
    (-1.0, False),
    (0, False),
    ("abc", False),
])
def test_amounts(amount, expected_valid):
    # логика теста
```
